# CI

What a change to the workflows, the dependency checks or the toolchain must know.

- **On a pull request:** `.github/workflows/ci.yml` runs `rust` (the build checks, clippy and the tests, `default` and `s3` builds) and `web` (the front end build). The `s3` job runs a `bitnamilegacy/minio` service, so `real_s3` runs against a real server there. `security.yml` runs `cargo deny check`, `npm audit --audit-level=high` (`npm-audit`), gitleaks over the whole history (`secrets`) and CodeQL (JavaScript and TypeScript, Actions). A new push to the pull request cancels its run in progress.
- **On a push to main** (ADR 0031): `ci.yml`'s `tested` job runs first. When the push is a merge whose tree is its pull request's head, and that head has a successful `ci.yml` pull request run, `rust` and `web` are skipped, since that pull request tested this tree. A main that moved since the pull request was tested, a squash or rebase merge and a direct push run them again. Then `e2e` (front end build, release build, the size check, Playwright's Chromium, `npm run test:e2e`, the Playwright results kept 14 days on failure) and `image` run whenever `rust` and `web` passed or were skipped: no pull request runs them, so a pull request learns of them after its merge. `security.yml` always runs `secrets`, the only scan of a direct push before Monday, and `codeql`, whose analysis of main is the alert list and the base each pull request's alerts are compared with. Its own `tested` job, the same check against `security.yml`'s runs, skips `cargo-deny` and `npm-audit` on a merge its pull request checked: an advisory published since waits for the next pull request or Monday. A direct push or a moved main gets them. A failed `tested` runs the jobs it gates, and `e2e` and `image` read only their direct `needs`, since `failure()` would count `tested` too. A push to main replaces a run of `ci.yml` still waiting there (`concurrency`), so a burst of merges tests the last one.
- **On a `v*` tag:** only `release.yml` (below); the other two take `push` on `main` only.
- **On schedule and by hand:** `security.yml` runs in full every Monday at 06:00 UTC, since an advisory can appear for code that did not change. `workflow_dispatch` runs either workflow in full, `rust` and `web` included. `dependabot.yml` opens grouped weekly updates for cargo, npm, the actions and the base images.
- **Minutes (step 69):** per merged pull request, 38.7 job minutes before (16.2 on the pull request, 22.5 on main) and 28.6 after (main 12.4), or 51.1 and 39.6 with each job rounded up to the minute, as GitHub bills private repositories; this one is public, so the minutes are free and the gain is runner time. Measured over the 28 pull requests merged from 2026-11-17 to 2026-11-27 (#19 to #52, the workflows' shape since `b012266`) from each job's `started_at` and `completed_at` in `gh api repos/MathieuMarthy/cadocs/actions/runs/<id>/jobs?filter=all`, re-runs included and `release.yml` left out. A pull request's runs are those of its branch between its creation and its merge, the main run is the one of its merge commit. "After" is the same sum without `rust`, `web`, `cargo-deny` and `npm-audit` on the 26 merges the check passes (run on each merge commit; #42 and #44 fail it), plus 15 seconds (1 billed minute) for each `tested`. In those 28 merges the main re-runs found nothing the pull request had missed: `rust` failed twice on trees that also passed (`revisions.rs:275` on #38's, whose pull request run was green, `rooms.rs:436` on #33's, green on its re-run), `cargo-deny` once on RUSTSEC-2026-0592, published between the two runs, which the next pull request hit too, and CodeQL twice on 2026-11-25, as a pull request did that day.
- **Settings:** none needed: a pull request merged red, or before its run ends, has no successful run on its head, so main tests it. A merge queue needs a repository owned by an organization; branches required to be up to date would have made 9 of the 28 pull requests merge `main` in and run everything again (ADR 0031).
- **Left open:** a green run proves the head merged with the base of its time, not the head's own tree, so two merges go untested (the `shortcut:` in `ci.yml`): a change merged then reverted on main while the pull request was open, and a pull request retargeted to main after its run (`edited` is not a default `pull_request` type, so no new run). `e2e` and `image` still fail only after the merge (#47's `e2e`). Flaky Rust tests seen on main: `a_restore_reaches_open_clients_and_keeps_the_previous_content` (`revisions.rs:275`, `s3`, 2026-11-14 and 2026-11-22), `sqlite_keeps_a_document_across_registries` (`rooms.rs:436`), `a_lost_grant_is_announced_and_closes_the_space` (`events.rs:129`, `s3`, 2026-11-13).
- **Pins:** actions are pinned by commit, with their tag as a comment, and Dependabot moves them. The Rust toolchain is pinned in `RUST_TOOLCHAIN` (1.99.1, the one the suite last passed clippy with): bump it on purpose, since new lints can fail the build. CodeQL has no Rust analysis here; clippy and cargo-deny cover Rust.
- **cargo-deny:** `deny.toml` allows only licenses compatible with AGPL-3.0 (ADR 0010), crates.io as the only source, and fails on advisories, except RUSTSEC-2026-0459, ignored with its reason until sqlx allows `libsqlite3-sys` 0.39 ([store notes](store.md)). Duplicate versions only warn. Every crate has `publish = false`, which `allow-wildcard-paths` needs for the workspace's path dependencies. Run it locally with `cargo deny check`.
- **npm audit:** the security workflow runs `node web/scripts/audit.ts`, which fails on a high or critical advisory unless it is listed there with its reason, as `deny.toml` does for Rust; npm has no ignore flag. GHSA-fc5q-39xc-vjpf (ReDoS in picomatch <= 4.0.7, no fixed version) is listed: only Vite uses it, at build time, on the project's own globs. The script names a listed id the report no longer has, so remove it once a fix lands. `npm audit fix --force` offered Vite 6, a breaking downgrade.
- **Not in CI:** the RAM benchmark (`bench/rss.sh`) needs a quiet machine, which shared runners are not ([benchmark notes](benchmark.md)).
- **Release:** `release.yml` runs on a `v*` tag: a draft release, then a matrix of `amd64`/`arm64` on native runners (`ubuntu-24.04-arm` is free for public repositories) by `default`/`s3`, each building the `Dockerfile` twice with buildx, `--target binary --output` for the archive and the full image pushed as `<version><suffix>-<arch>`, then `imagetools create` for the multi-architecture tags, and the release is published. It uses no third-party action: `gh` and the runner's buildx. The `Dockerfile` has no BuildKit cache mounts, so a plain `docker build` without buildx works too (this machine has no buildx). Base images are pinned by digest, and Dependabot's `docker` entry moves them. The build stage uses bookworm so binaries need glibc 2.36 only; the runtime is `distroless/cc-debian13:nonroot`.
- **Image check:** `scripts/check-image.sh [image]` runs the image, does the first-run setup over REST, then `backup` inside the container and `restore` into a new volume, and checks the account came back. The backup goes to a named volume on `/home/nonroot`, which takes that folder's owner (uid 65532) from the image, so the container can write it and no host file is left owned by another user. `ci.yml`'s `image` job runs it after each push to main, and `release.yml` runs it on each architecture and flavor before pushing. Its last two runs are ADR 0025: a volume first mounted on `/mnt`, which root owns, and filled as root (`--user 0:0 -e CADOCS_RUN_AS=`), then a `mktemp` folder of the caller as a bind mount, with the process's uid read through `docker top`. It uses port 38931 on the host, so two runs on one machine collide; GitHub's runners give each job its own. The `image` job skips pull requests, as `e2e` does, so an image broken by a pull request shows on main.
- **Build checks:** `scripts/check-build.sh <default|s3>` reads `cargo tree -e normal` (the in-memory S3 is a dev-dependency) and fails if a default build depends on `rusty-s3` or `reqwest`, or an `s3` build does not; the `rust` job runs it for its flavor. With a binary as second argument it fails over 30,000,000 bytes, and on S3 code found by the panic locations a stripped binary keeps (`rusty-s3`, `reqwest`, `cadocs-files/src/s3`). The `s3` flavor must show them, so a marker that stops matching fails `release.yml` instead of passing silently. The `e2e` job checks the default release binary, so a pull request learns of the size only after its merge.
- **Upgrade fixtures:** after each release is published, run `scripts/make-upgrade-fixture.sh <tag>`, add the tag to `RELEASES` in `crates/cadocs-server/tests/upgrade.rs` and commit the folder. The script runs that release's own published binary and makes the same data each time, so the test checks every fixture the same way. Data that only a later release can make gets checks of its own, for the fixtures that hold it. The test raises the trash and revision retention to their maximum, since fixture dates never move. It never checks an invitation or a session, which expire.
