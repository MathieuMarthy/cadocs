# CI

What a change to the workflows, the dependency checks or the toolchain must know.

- **Workflows:** `.github/workflows/ci.yml` runs clippy and the tests, default and `s3` builds, and the front end build on every pull request. On a push to main or by hand it adds the end-to-end campaign: front end build, release build, Playwright's Chromium, `npm run test:e2e`, with the Playwright results kept 14 days on failure. The `s3` job runs a `bitnamilegacy/minio` service, so `real_s3` runs against a real server there. `security.yml` runs `cargo deny check`, `npm audit --audit-level=high`, gitleaks over the whole history and CodeQL (JavaScript and TypeScript, Actions) on every pull request, on every push to main, and every Monday, since an advisory can appear for code that did not change. `dependabot.yml` opens grouped weekly updates for cargo, npm and the actions.
- **Pins:** actions are pinned by commit, with their tag as a comment, and Dependabot moves them. The Rust toolchain is pinned in `RUST_TOOLCHAIN` (1.99.1, the one the suite last passed clippy with): bump it on purpose, since new lints can fail the build. CodeQL has no Rust analysis here; clippy and cargo-deny cover Rust.
- **cargo-deny:** `deny.toml` allows only licenses compatible with AGPL-3.0 (ADR 0010), crates.io as the only source, and fails on advisories, except RUSTSEC-2026-0459, ignored with its reason until sqlx allows `libsqlite3-sys` 0.39 ([store notes](store.md)). Duplicate versions only warn. Every crate has `publish = false`, which `allow-wildcard-paths` needs for the workspace's path dependencies. Run it locally with `cargo deny check`.
- **Not in CI:** the RAM benchmark (`bench/rss.sh`) needs a quiet machine, which shared runners are not (`docs/notes/benchmark.md`). Not run yet on GitHub when this was written: the first push shows whether a matrix service with an empty image is skipped as intended, and whether the bitnami image starts as it does locally.
- **Release (step 21):** `release.yml` runs on a `v*` tag: a draft release, then a matrix of `amd64`/`arm64` on native runners (`ubuntu-24.04-arm` is free for public repositories) by `default`/`s3`, each building the `Dockerfile` twice with buildx, `--target binary --output` for the archive and the full image pushed as `<version><suffix>-<arch>`, then `imagetools create` for the multi-architecture tags, and the release is published. It uses no third-party action: `gh` and the runner's buildx. Not run yet when this was written. The `Dockerfile` has no BuildKit cache mounts, so a plain `docker build` without buildx works too (this machine has no buildx). Base images are pinned by digest, and Dependabot's `docker` entry moves them. The build stage uses bookworm so binaries need glibc 2.36 only; the runtime is `distroless/cc-debian13:nonroot`.
