# Server

What a change to HTTP, sockets, sessions or administration must know.

- **Server:** `cadocs-server` is a library plus the `cadocs` binary. `serve::<S, A, E>` takes the store, the authorizer and the embedded assets as type parameters, so tests pass a failing store and fixture assets. One task per socket does everything (`ws.rs`), because `Connection::next` takes `&mut self`: a blocked send stops that socket's reads, up to `CADOCS_PING_TIMEOUT_SECS`. The `tungstenite` version must stay the one axum uses, or the downcast behind `1009` stops matching (a test covers it). `serve` flushes rooms before it waits on HTTP, and bounds that wait, because a stalled client would otherwise hold up shutdown. A frame far over the limit can lose its `1009` to a TCP reset: `recv` ends at the capacity error, so the rest is never read.
- **Page socket:** `/ws/pages/{page}` sits behind `api::check_origin` and `session::require` as route layers, in that order, and the handler reads `Extension<CurrentSession>`. So the refusals are the JSON ones of REST, and the upgrade touches the session. `tests/page_socket.rs` has real roles over real sockets.
- **HTTP foundation:** `api.rs` holds `ApiError` (build from `ErrorCode`, return it with `?`) and `api::router`: add REST routes before its `finish` call, which only reaches the routes that already exist. `api::rate_limit` is a route layer over `(Arc<RateLimiter>, Arc<HttpConfig>)`, and `api::count_request` does the same from a handler. Test a limit over a real socket, as `tests/auth.rs` does, since only `serve` provides the real `ConnectInfo`. The burst and refill of each limiter are chosen where it is wired. `RateLimiter` counts an IPv6 /48 as one client and tracks 4096 clients at most. Past that a newcomer waits, so 4096 live addresses or sites can hold up strangers, but never reset a client. `security::add_headers` covers every response and leaves alone what a handler set. `PublicUrl::allows` accepts a missing `Origin`, so REST must not rely on it alone. `/api/v1/` needs its own line in `router`, because a nest cannot reach it, so it answers `404` to any `Origin`.
- **Accounts and sessions:** add a route that needs a user to `authenticated` in `api/auth.rs`, or put `session::require` on it: that layer checks the session and CSRF, and handlers read `Extension<CurrentSession>`. `AccountStore` (`cadocs-store`) sits beside `DocStore`, and the server needs both. Read bodies with `api::JsonBody`, whose refusals are in the error shape. A storage error becomes `503` through `From<StoreError>`. Whatever depends on a password check must hold when the write happens, because a hash can wait 10 seconds: `create_session`, `UpdateBasis` and `use_password_reset` re-check inside the write. Nothing tells a client that first-run setup is pending, as `GET /session` answers `401` either way: step 11 needs a public read of `has_users`. A failed session touch retries on each request, each waiting up to 1 second, and has no back-off.
- **Instance administration:** `api/admin.rs` holds `/admin/users`, behind `session::require` and a role check. `api::PageQuery` and `api::Page` are the pagination of every list, and `api::PathParam` reads a path parameter with its refusal in the error shape. `axum` has no `query` feature, on purpose. A reset link is `<public url>/reset-password/<token>`, and step 11 must serve that page, which posts to `/auth/password-reset/{token}`. `assets::serve` answers `404` for it today. `SqliteStore::open_existing` is for commands beside a live server: it neither creates nor migrates. The links an admin made go when they are disabled, demoted or deleted. An admin who deletes or disables themself through `/admin/users` gets no removal cookie, unlike `DELETE /me`: the next request is a `401`, which step 11 must handle. `tests/common` holds the REST test client.
