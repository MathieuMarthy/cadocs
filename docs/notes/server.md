# Server

What a change to HTTP, sockets, sessions or administration must know.

- **Server:** `cadocs-server` is a library plus the `cadocs` binary. `serve::<S, A, E>` takes the store, the authorizer and the embedded assets as type parameters, so tests pass a failing store and fixture assets. One task per socket does everything (`ws.rs`), because `Connection::next` takes `&mut self`: a blocked send stops that socket's reads, up to `CADOCS_PING_TIMEOUT_SECS`. The `tungstenite` version must stay the one axum uses, or the downcast behind `1009` stops matching (a test covers it). `serve` flushes rooms before it waits on HTTP, and bounds that wait, because a stalled client would otherwise hold up shutdown. A frame far over the limit can lose its `1009` to a TCP reset: `recv` ends at the capacity error, so the rest is never read.
- **Page socket:** `/ws/pages/{page}` sits behind `api::check_origin` and `session::require` as route layers, in that order, and the handler reads `Extension<CurrentSession>`. So the refusals are the JSON ones of REST, and the upgrade touches the session. `tests/page_socket.rs` has real roles over real sockets.
- **HTTP foundation:** `api.rs` holds `ApiError` (build from `ErrorCode`, return it with `?`) and `api::router`: add REST routes before its `finish` call, which only reaches the routes that already exist. `api::rate_limit` is a route layer over `(Arc<RateLimiter>, Arc<HttpConfig>)`, and `api::count_request` does the same from a handler. Test a limit over a real socket, as `tests/auth.rs` does, since only `serve` provides the real `ConnectInfo`. The burst and refill of each limiter are chosen where it is wired. `RateLimiter` counts an IPv6 /48 as one client and tracks 4096 clients at most. Past that a newcomer waits, so 4096 live addresses or sites can hold up strangers, but never reset a client. `security::add_headers` covers every response and leaves alone what a handler set. `PublicUrl::allows` accepts a missing `Origin`, so REST must not rely on it alone. `/api/v1/` needs its own line in `router`, because a nest cannot reach it, so it answers `404` to any `Origin`.
- **Accounts and sessions:** add a route that needs a user to `authenticated` in `api/auth.rs`, or put `session::require` on it: that layer checks the session and CSRF, and handlers read `Extension<CurrentSession>`. `AccountStore` (`cadocs-store`) sits beside `DocStore`, and the server needs both. Read bodies with `api::JsonBody`, whose refusals are in the error shape. A storage error becomes `503` through `From<StoreError>`. Whatever depends on a password check must hold when the write happens, because a hash can wait 10 seconds: `create_session`, `UpdateBasis` and `use_password_reset` re-check inside the write. `GET /auth/setup` tells a client that first-run setup is pending, as `GET /session` answers `401` either way. A failed session touch retries on each request, each waiting up to 1 second, and has no back-off.
- **Instance administration:** `api/admin.rs` holds `/admin/users`, behind `session::require` and a role check. `api::PageQuery` and `api::Page` are the pagination of every list, and `api::PathParam` reads a path parameter with its refusal in the error shape. `axum` has no `query` feature, on purpose. A reset link is `<public url>/reset-password/<token>`, a route of the front end. `SqliteStore::open_existing` is for commands beside a live server: it neither creates nor migrates. The links an admin made go when they are disabled, demoted or deleted. An admin who deletes or disables themself through `/admin/users` gets no removal cookie, unlike `DELETE /me`: the next request is a `401`, which the front end treats as a session that ended. `tests/common` holds the REST test client.
- **Events socket:** `/ws/events?workspace=` is in `ws.rs`, behind the same layers as the page socket. `cadocs-collab::events` holds the hubs, reached through `DocRegistry`: `publish`, `publish_after_recheck`, `join_events`. A handler that changes the tree or a space publishes once it is stored, and the event of a rename comes from the flush, never from `PATCH`. A new space has no reader yet, so `space.created` goes through `publish_after_recheck` with `access_changed`. A step that changes pages outside a handler must publish the same events as the handler, as `Cleanup::purge_trash` does for `purge_page`. A pass costs two or three queries per events socket with no dedupe, and step 23 should measure it. An `Event` builds its JSON once. `tests/events.rs` floods the hub with a single-threaded runtime to force `resync`, because a real TCP client takes far too long to fall behind.
- **Jobs:** `cadocs-jobs` holds `JobQueue`, `Worker` and the `Handler` trait, and `Cleanup` is the handler of the two recurring jobs. `start_jobs` in `lib.rs` starts the worker beside `serve`, not inside it, so `serve` needs no `JobStore` and `FlakyStore` stays as it is. It returns the queue, which `main` drops: the reindex of step 18 is queued by the store, inside the transaction of a flush or a language change, and `JobStore::jobs_added` wakes the worker for any job a write adds, `enqueue` included. `ServerJobs` is the handler `start_jobs` runs: `Index` for `reindex_page`, `Cleanup` for the rest. A new kind goes in a handler's `run`, and one worker runs one job at a time, so a slow job holds up the next. `JobStore` runs on the writer, reads too, because the poll must not keep a reader connection open at idle. It checks no role. A store failure while recording the end of a job leaves it `running` until the next start, which runs it again.
- **Search:** `api/search.rs` reads `q` and `space` by hand, as `PageQuery` does. The route needs `WorkspaceStore` for the language and `SearchStore` for the query, so `serve` and `router` now ask for `SearchStore` too, and `FlakyStore` delegates it. `tests/common` sets `with_reindex_delay(100 ms)`, so every server test indexes its pages soon after their edits: `tests/search.rs` waits for results with `found`.
- **Attachments:** `cadocs-files` holds `FileStore`, object safe so `AppState` keeps an `Arc<dyn FileStore>` and tests swap in a failing one (`FullDisk` in `tests/attachments.rs`). `LocalFileStore::open` empties `data/tmp`, so it runs after the lock. An upload is the raw body (`api/attachments.rs`), with no `DefaultBodyLimit`: `put` enforces the limit while streaming, and its temporary file goes on drop, so a client that leaves mid-upload leaves nothing. A refusal that leaves a body unread can reach a test client as a reset: `announced` and `chunked` in the attachment tests send nothing, or no more, past what the server reads. `purge_orphan_files` is the third recurring job of `Cleanup`, which now takes the file store.
- **Revisions:** `api/revisions.rs`, with the restore itself in `cadocs_jobs::restore`: it checks `revision_to_restore`, decodes the revision, opens the room, checks again, keeps the current content with `capture`, then calls `rewrite`, whose transaction also reads what it replaces, so edits typed since the capture are kept as one more revision. Decoding goes through `decode_bounded`, under a turn of `CADOCS_DOC_READS`. `cadocs-content` is now a dependency of the server, for `to_html` and `replace_page`. `tests/revisions.rs` sets `CADOCS_REVISION_PAUSE_SECS=0`, a revision after each flush; `tests/common` passes `config.revisions` to the store.
