# Collab

What a change to rooms, sync or Yjs must know.

- **Collab:** `DocRegistry::connect(doc, mode, user, session)` returns a `Connection`, and the server only moves bytes: `receive(frame)` (an `Err(Close(code))` means close with it) and `next().await` (cancel safe, `Frame` or `Close`). `DocRegistry::set_title` is the only write from the server. Another one goes through `enter`, which runs under the registry lock, and through `Room::enqueue`, so it is stored and broadcast like an edit. Hide `yrs` behind such methods: `cadocs-server` has it as a dev dependency only. A flush that gets `PageNotFound` calls `Room::abandon`, which closes the sockets with `4404`: a recheck closes them earlier, this stays as the last resort. The room keeps one author per queue, the last one, so a batch of two users credits one. `set_title` refuses a title root that holds more than text, which only a crafted client can write: `PATCH` then answers `500` for that page, and nothing resets it yet. `PATCH` checks the role again once the room is live, because a write to a room cannot sit in a database transaction: only a demotion or a trash in the few instructions left can still let the edit land, and `append_updates` ignores `deleted_at`.
- **yrs 0.28:** `yrs::sync` has `Awareness`, `Message`, `SyncMessage`, `MessageReader`, `DefaultProtocol` and the `Protocol` trait. Filter around `Protocol::handle_message` to reject `SyncStep2` and `Update` in read-only mode. `Doc` is `Send + Sync`. Enable the `sync` feature if the async or observer APIs require it.
- **yrs hardening:** yrs 0.28 can panic and even segfault on crafted updates, in release too, and `catch_unwind` only covers panics. Write access means trust, and this risk is accepted (ADR 0014). Keep unwinding on. `mutated_frames_do_not_break_the_room` pins client ids so it does not crash at random. A dependency that never arrives blocks compaction until the log reaches 4 times `compact_updates`, and a stored row that cannot be applied (`skipped_row`) still blocks it for good. Awareness ownership is by user, because a reconnecting client reuses its id, so two tabs of one user can overwrite each other. `user` in a state is not validated, only `cursor` is.
- **y-websocket** appends `/<room>` to the server URL. By default it stops for good on close codes 4400 to 4499, so `web/src/main.ts` passes `shouldReconnect`, and any other client of this server must too. The MVP must still show `4401`, `4403` and `4404` in the page: today the status stays at "offline, retrying".
- **Yjs document layout:** root types `title` (`Y.Text`) and `default` (`XmlFragment`, TipTap's default field). See `docs/DATA_MODEL.md`.
- **Socket RAM:** tungstenite's write buffer keeps the capacity of the largest frame sent, and no option shrinks it, so each socket holds about one SyncStep2 of its document for its whole life. Measured at 62 KiB per socket on the 20 KB benchmark document.
- **Reader:** `DocRegistry::read(doc, action)` hands `action` a private `yrs::Doc` under `doc_reads`, for steps 16, 18 and 19. `action` is synchronous and runs on an async thread, so it should take what it needs and return: heavy work belongs after the read. A document with no page reads as empty: the caller checks the page first. What waits for a dependency is left out of a live read, and a stored row that cannot be applied is skipped, as in a room load.
- **Rewrites:** `DocRegistry::rewrite(doc, user, bytes, action)` runs `action` on the room's `TransactionMut` through `enter`, as one edit by `user`; `set_title` is the same path (`Room::change`). A panic in `action` answers `CorruptDocument`, and what it wrote before still goes out. The server never names a yrs type: `cadocs-jobs` passes `cadocs_content::yjs::replace_page`. `DocRegistry::bounded(action)` runs work as heavy as a read under the same `doc_reads` turn. A restore reads the AST and encodes the full state inside `rewrite`, under the room and registry locks, beside `replace_page`: about twice the pause a rewrite already made, and the room briefly holds the old state next to the new content. Step 23 should time it on a large page.
