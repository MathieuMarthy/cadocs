# Web

What a change to the front end or its tests must know.

- **Shell:** Svelte 5 with runes (ADR 0004), mounted on `body` by `main.ts`. `App.svelte` holds every route in `resolve`, which also does the redirects: setup while no account exists, login with `?next=` without a session, back to `safeNext(next)` once there is one. So a screen logs in by calling `signIn`, and never navigates for it. `lib/router.svelte.ts` has no dependency: it catches clicks on same-site links, and the server answers `index.html` for any path that is not a file (`assets.rs`, which lists the first segments that are not routes: add `s` with public shares). `lib/api.ts` keeps the CSRF token and sends every `unauthenticated` answer to `sessionEnded`, so a screen need not handle a lost session. Only a `signOut` after a real `POST /auth/logout` or a `refreshSession` that failed may drop the session: the server decides, not the screen. `lib/form.svelte.ts` holds a form's busy state and refusals, and shows a field's code with spaces (`too short`). Screens without a sidebar use `Solo.svelte`, the others `Shell.svelte`. `Source.svelte` has the source link and the theme button, and must stay on every screen (ADR 0010). `vite.config.ts` builds the link from the commit, or from the tag without Git. The theme is `data-theme` on `<html>`, over `light-dark()` in the tokens, set before the first paint by `public/theme.js`, a file because the CSP refuses inline scripts.
- **Type checks:** `tsc` skips `.svelte` files, and `svelte-check` needs TypeScript 5 or 6 while the project has 7, so it is not a dependency. Run it by hand after changing a component: `npx -y -p typescript@6 -p svelte-check@4.7.8 -p svelte@5.57.3 svelte-check --workspace . --tsconfig ./tsconfig.json` from `web/`.
- **Left for later steps:** step 14 must handle `4409`, which still shows `offline, retrying` and leaves a demoted reader's editor writable, while the server drops what they type. Step 12 replaces the space list of `Workspace.svelte`, which reads only the first page and ignores `next_cursor`.
- **Page view:** `routes/Page.svelte` and `editor/collab.ts`, loaded on demand, so a login does not download TipTap. Still the prototype page, with `guest-` names, until step 14. `?page=<id>` picks it. It reads `GET /pages/{id}` before opening the socket, and again every 3 failed connections, because a socket cannot read the status of a failed upgrade. Only `401` and `404` stop it. `4401` goes to login, `4403` and `4404` replace the page with a message. `disableBc` is on, so two tabs of one browser really go through the server. Awareness holds `user: { name, slot }`, where `slot` (1 to 3) picks the presence color. The title is a plain input bound to `Y.Text` in `web/src/title.ts`.
- **Browser tests:** Playwright reads the browser path from `CHROMIUM_PATH` through `executablePath`, and uses its own Chromium when unset. Any Chromium-based browser works.
- **Slow browser start:** Helium, in a new process, can stall every request for 5 seconds or more, static files too, and then load the page a second time. It does not come from the server, and `requestfinished` shows it. A page opens its socket after three round trips, so this now falls before the socket, and `expect.timeout` is 30 seconds. For a quick loop, `CADOCS_BIN=../target/debug/cadocs` reads `web/dist` at run time and needs no release build.
- **End-to-end tests:** `web/e2e/` runs the real binary, on its own port and temporary data folder (`server.ts`, `CADOCS_BIN` picks another binary). `TestServer` runs first-run setup on the first `session()`, and `page(name)` creates a page per name, so tests keep naming their rooms. Node's `WebSocket` sends the cookie through `webSocketClass()`, passed as `WebSocketPolyfill`, and a browser gets it from `addCookies`. `compat.test.ts` uses `node:test` with the real `yjs` and `y-websocket`, and needs Node 22.18 or later for type stripping and `node:sqlite`. `browsers.spec.ts` uses Playwright, with two real browser processes. `shell.spec.ts` covers the shell, and `TestServer` gives it `call`, `invite` and `addMember` for what the test does not go through the interface for. An open client resends its whole document when it reconnects, so a test about the disk must have no client left when the server comes back. A paragraph's text holds the label of a remote caret: read it with `bodyLines`. Do not `goto("about:blank")` before another `goto`: the browser sometimes commits it twice, which aborts the next navigation.
